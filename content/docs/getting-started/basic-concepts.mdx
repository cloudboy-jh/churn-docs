Understanding these core concepts will help you get the most out of Churn.

## Repository Detection

Churn automatically detects Git repositories when you run it. It uses repository information to:

- Determine which files to analyze
- Identify staged files for `--staged` mode
- Generate context-aware suggestions
- Create relative file paths in reports

**Requirements**:
- Must be run inside a Git repository
- Repository must be initialized (`git init`)

## Analysis Modes

Churn supports three analysis modes:

### Full Analysis

Analyzes all files in your repository (excluding ignored patterns).

```bash
churn run
```

**When to use**:
- First-time analysis
- Pre-release quality checks
- Comprehensive code reviews
- Major refactoring projects

**Cost implications**: Analyzes entire codebase, highest API usage

### Staged Analysis

Analyzes only files in your Git staging area.

```bash
churn run --staged
```

**When to use**:
- Daily development workflow
- Before commits
- Quick quality checks
- Cost-conscious analysis

**Benefits**: 80-90% cost savings compared to full analysis

### File-Specific Analysis

Analyzes specific files or patterns.

```bash
churn run --files "src/components/**/*.tsx"
```

**When to use**:
- Targeting specific modules
- Reviewing changed files
- Analyzing new features
- Debugging specific areas

## Suggestion Categories

Churn categorizes findings into five types:

### Refactor

Code structure improvements, design pattern suggestions, and maintainability enhancements.

**Examples**:
- Extract complex functions
- Apply DRY principles
- Improve naming conventions
- Simplify conditional logic

### Bug

Potential bugs, logic errors, and correctness issues.

**Examples**:
- Off-by-one errors
- Null pointer risks
- Race conditions
- Type mismatches

### Optimization

Performance improvements and efficiency gains.

**Examples**:
- Algorithm improvements
- Caching opportunities
- Unnecessary computations
- Memory optimizations

### Style

Code style and formatting improvements.

**Examples**:
- Consistent formatting
- Naming conventions
- Import organization
- Comment quality

### Documentation

Missing or inadequate documentation.

**Examples**:
- Missing function docs
- Unclear comments
- Outdated documentation
- Missing README sections

## Severity Levels

Each suggestion is assigned a severity:

### High

Critical issues requiring immediate attention.

**Examples**:
- Security vulnerabilities
- Data loss risks
- Breaking bugs
- Critical performance issues

### Medium

Important issues that should be addressed soon.

**Examples**:
- Moderate bugs
- Refactoring opportunities
- Performance improvements
- Missing error handling

### Low

Minor improvements and nice-to-haves.

**Examples**:
- Style inconsistencies
- Documentation gaps
- Minor optimizations
- Code clarity improvements

## Reports and Exports

Churn generates comprehensive reports in multiple formats:

### JSON Report

Machine-readable format for programmatic access.

**Location**: `.churn/reports/churn-reports.json`

**Use cases**:
- CI/CD integration
- Custom tooling
- Data analysis
- Automated processing

### Markdown Report

Human-readable format for sharing.

**Location**: `.churn/patches/report-*.md`

**Use cases**:
- Team reviews
- Documentation
- Release notes
- Pull request comments

### Git Patch

Applicable changes in Git patch format.

**Location**: `.churn/patches/changes-*.patch`

**Use cases**:
- Applying suggestions with Git
- Version control integration
- Code review workflows

## Local-First Architecture

Churn is built with a local-first philosophy:

### No Cloud Backend

- All data stored locally
- No remote servers
- No account required
- Complete privacy control

### Storage Locations

**Global config**: `~/.churn/config.json`
- API keys
- Default settings
- User preferences

**Project config**: `.churn/config.json`
- Project settings
- Last run metadata
- Custom ignore patterns

**Reports**: `.churn/reports/`
- Latest analysis results
- Historical data

**Cache**: `.churn/cache/`
- Cached analysis results
- Content hashes

**Exports**: `.churn/patches/`
- JSON exports
- Markdown reports
- Git patches

## Caching System

Churn uses smart content-based caching:

### How It Works

1. Files are hashed with SHA-256
2. Hash is checked against cache
3. If match found, cached result used
4. If no match, file is analyzed

### Benefits

- **70% cost savings** on reruns
- **Faster analysis** for unchanged files
- **Consistent results** for same content
- **Automatic cache management**

### Cache Duration

- Cache persists for **30 days**
- Automatically cleaned after expiration
- Manual clearing available

### Cache Invalidation

Cache is invalidated when:
- File content changes
- 30 days have passed
- Cache is manually cleared
